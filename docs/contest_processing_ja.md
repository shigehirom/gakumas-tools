# gakumas-tools におけるコンテスト処理の技術解説

現在の `gakumas-tools` (Web GUI) および CLI におけるコンテスト関連の処理について、実装の詳細と両者の差分をまとめます。

---

## 1. gakumas-tools (Web GUI) のコンテスト処理

Web GUI におけるコンテスト処理は、主に **「対話的な単一編成の検証と可視化」** を目的としています。

### A. シミュレーションエンジン (`gakumas-engine`)
Web 側では `gakumas-engine` パッケージを直接利用し、ブラウザ上の Web Workers (`gakumas-tools/simulator/worker.js`) を介してシミュレーションを実行します。
- **ロジックの共通性:** ステージ進行、スキルの実行、バフ計算などは `StageEngine` クラスに集約されており、ゲーム内ロジックを忠実に再現しています。
- **戦略 (Strategy):** デフォルトで `HeuristicStrategy` が使用されます。これは 3 手先までの全パターンを探索し、最も高い「期待スコア（現在のスコア + 状態異常やバフの重み付け合計）」を持つカードを選択するアルゴリズムです。
- **可視化:** `StagePlayer` が生成するログ（`logs`）とグラフデータ（`graphData`）を元に、ターンごとのスコア推移やバフの蓄積状況を UI 上で詳細に確認できます。

### B. 編成 (Loadout) の生成ロジック (`LoadoutContext.js`)
ユーザーが選択したメインメモリとサブメモリを合体させ、シミュレータに渡す `Loadout` オブジェクトを生成します。
- **ステータス計算:** メインメモリのステータスを 100%、サブメモリのステータスを 20%（切り捨て）として加算します。
- **カード・アイテムの集約:** Pアイドル固有のアイテム/カードに加え、メインメモリのアイテムと、メイン・サブ両方のスキルカード（計 12 枚）を統合します。

---

## 2. CLI (packages/cli) のコンテスト処理

CLI における `contest` コマンドの核心は、**「大量のメモリー組み合わせによるバッチ最適化とキャッシュ」** にあります。

### A. 並列処理と最適化 (`optimize-memories-parallel.mjs`)
単一の編成ではなく、指定されたアイドルやプランに合致する全メモリーの組み合わせ（メイン × サブ）を全当たりで計算します。
- **Worker Threads:** `worker_threads` を利用し、CPU コア数に合わせて並列にシミュレーションを実行します。
- **プロセスの流れ:**
    1. MongoDB またはローカルから対象メモリー群をロード。
    2. 全組み合わせを生成し、未計算のハッシュ（MainHash + SubHash + StageId + Runs + SupportBonus）を抽出。
    3. `optimize-worker.mjs` でシミュレーションを実行。

### B. キャッシュ戦略 (MongoDB Integration)
計算負荷が高いため、詳細な結果を MongoDB の `simulation_results` コレクションにキャッシュします。
- キャッシュがある場合は再計算をスキップし、過去の計算結果（平均、最小、最大、中央値）を即座に取得します。

---

## 3. Web GUI と CLI のロジック的な差分

エンジニアリングの観点から見た、両者の主要な差分は以下の通りです。

| 項目 | Web GUI (gakumas-tools) | CLI (packages/cli) |
| :--- | :--- | :--- |
| **実行主体** | ブラウザ (Web Workers) | Node.js (Worker Threads) |
| **計算単位** | 単一 Loadout (対話的) | メモリの総当たり組み合わせ (バッチ) |
| **シミュレーションロジック** | `gakumas-engine` (共通) | `gakumas-engine` (共通) |
| **思考ルーチン** | `HeuristicStrategy` / `Manual` | `HeuristicStrategy` 固定 |
| **パフォーマンス最適化** | 可視化のために詳細なログを保持 | `logger.disable()` でオーバーヘッドを排除 |
| **データの永続化** | URL パラメータ / ブラウザ DB | MongoDB (永続キャッシュ・履歴保存) |
| **ステータス合算ロジック** | `LoadoutContext` で UI 制御 | `optimize-worker.mjs` で内部計算 |

### 実装レベルでの特筆すべき違い

1.  **ロガーの挙動:**
    Web GUI ではシミュレーション過程の「なぜそのカードを選んだか」を表示するために詳細なログを残しますが、CLI では数万回の試行を行うため、`engine.logger.disable()` を呼び出してロギング処理のオーバーヘッドを排除しています。
2.  **サンプリング数 (Runs) の扱い:**
    Web GUI はその場での素早い検証を優先しますが、CLI ではデフォルトで大きな n 数 (1000~3000) を設定し、統計的信頼性を重視しています。
3.  **環境の差異:**
    CLI 版は MongoDB への接続が前提となっており、計算済みのハッシュ値をキーとした結果の再利用が組み込まれています。
